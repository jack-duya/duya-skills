# 渡鸦组件更新

当用户说“更新渡鸦”“升级 duya”“检查新版本”时使用本说明。只更新渡鸦的主技能及安装包声明的薄入口，不更新其他技能、MCP 注册信息或用户记忆。

## 两个动作

只检查，不创建目录或修改安装：

```text
python -B -X utf8 "<duya目录>/tools/update.py" check
```

用户已要求更新时，完成更新并报告结果：

```text
python -B -X utf8 "<duya目录>/tools/update.py" apply
```

路径必须使用当前实际加载的技能目录，不能凭印象选择另一个同名安装。可以用 `--target "<实际duya目录>"` 明确目标；测试或自定义备份位置使用 `apply --backup-root "<独立目录>"`。

用户只问“有没有更新”，只执行 `check`。用户明确要求更新，不再反复请求许可。检查失败时不把网络故障解释为已经最新；报错说明当前阻碍即可，不要求用户提供密码或 Token。

## 它怎样更新

1. 从官方 `jack-duya/duya-skills` 的 `main` 获取完整 commit SHA，再按该 SHA 读取包清单和下载 ZIP；不会一边检查旧 main、一边安装后来变化的 main。
2. 只处理包清单 `components` 中的 `duya` 和 `duya-*` 组件。每项都检查 `SKILL.md` 名称，薄入口检查 `metadata.duya_component: true`。不执行下载包中的脚本。
3. 下载大小、解压大小、文件数、路径逃逸、ZIP 中的符号链接与特殊文件都在写入安装前检查。同名兄弟目录不属于渡鸦时停止全部更新。
4. 为所有组件准备新目录：复制旧内容、保留未知个人文件，再覆盖新版官方文件。只有旧状态明确登记的官方文件才允许随新版删除。首次旧版没有状态时，未知文件继续保留。
5. 将旧组件完整备份，再逐项替换。失败时恢复已经替换的组件；如文件占用等原因导致恢复仍失败，报告 `rollback_incomplete` 和可恢复目录，不声称成功。
6. 每项写入 `.duya-update-state.json`，记录版本、固定 commit、官方文件清单与散列。整个技能目录外的用户记忆、宿主 MCP 配置保持不变；目录中的既有 `.mcp.json` 也保留原样。

默认备份位于 `~/.duya/updates/<目标目录标识>/<时间>/`。里面的 `update.json` 记录目标位置和被替换文件；同目录的组件副本保存更新前内容。用户改过的官方文件会由新官方文件替换，旧修改在完整备份中保留；不要声称已自动理解并合并这类修改。

重复应用已经安装过的同一 commit，不视为强制重置：该次安装之后发生的本地修改继续保留，并在 `local_changes_preserved` 中列出。只有切换到新官方修订时，才备份并替换对应官方文件。

## 不同安装方式

| 当前实际安装 | 处理 |
|---|---|
| 普通复制目录、Skills CLI 目录 | 运行本更新器，只管理包清单内组件；不用全局 `skills update` 顺带升级其他产品 |
| 主技能目录是软链接 | 解析并检查实际目标；更新该目标，不替换主技能链接本身 |
| `.agents`、`.codex`、`.claude`、`.cursor` 中已有主技能桥接 | 仅在该处 `skills/duya` 已存在且指向同一核心目录时补齐薄入口；不创建新客户端安装 |
| 完整 Git checkout | 更新器核验工作树干净且 origin 正确后返回 `git_update_required`；宿主在该仓库 fetch 后 fast-forward 到返回的固定 SHA，再检查技能入口，不运行 reset 或 clean |
| 宿主 `plugins/cache` 中的安装 | 可只读检查版本；拒绝直接写缓存，使用该宿主的原生插件更新途径；修改缓存不等于成功升级插件 |
| 已有薄入口链接到同一核心旁的对应渡鸦组件 | 保留链接，只更新其实际组件；这是 Skills CLI 常见的客户端桥接方式 |
| 薄入口链接到其他位置、核心旁的组件本身是链接、或组件内部含链接 | 停止并说明需要检查链接所属关系，避免跨目录覆盖 |

使用本更新器后，Skills CLI 的全局锁文件不会被伪造或重写。本更新器依据自己的组件状态核对 commit；以后混用其他安装工具时，要重新确认它操作的安装目录。原先仅用 Skills CLI 安装、没有本更新器状态时，报告可能显示当前修订未知，这不等于安装损坏。

## 怎样向用户报告

- `current`：官方固定 commit 与安装状态一致、或本次比较无需替换。
- `updated`：说明旧版到新版、更新了哪些入口、备份位置；告诉用户新开对话使用新入口。宿主没有及时刷新时再重启，不能承诺已加载进当前正在进行的对话。
- `git_update_required`：文件尚未更新；由宿主继续执行返回的受控 Git 步骤，完成后复核，不把它当作成功。
- `error`：说明实际原因与安装是否已经恢复，不编造成功结果。

`check` 的当前 commit 只来自已有安装状态；没有状态时明确修订未知。未知文件的保留表示文件还在，并不保证用户自定义脚本或主题与新版 API 自动兼容。
